音乐舱三个统一：完整实现、发布流程与线上验收手册

音乐舱的“三个统一”已经完成开发，并在 2026 年 11 月 1 日执行过一次生产发布：统一版本清单、统一构建入口、统一部署入口。它解决的是“构建了什么、切换了什么、出了问题怎样核实和恢复”，不是把所有组件强行标成同一个版本。

本文同时是实现说明和线上验收手册。普通使用者从第一节开始；负责发布的人继续看版本、命令和异常处理。文中的生产结果是 2026 年 11 月 1 日这次发布的证据快照，不是长期有效的健康保证。示例中的 /absolute/... 路径需要替换成本机实际位置；公开文章不附生产 target、凭据、服务器地址或原始数据。

一、先在线上验收：从能打开到真正能听

1. 适用范围与停止条件

主要验收入口是音乐舱新站，原有旧站作为兼容回归入口。两个站目前共用 TS 音频网关，但播放器实例和用户数据独立。旧站列表与新站列表不同，不等于数据丢失；不要为了让截图一致而覆盖其中一边。

出现以下情况时，停止反复点击发布、登录或刷新凭据：歌单/历史明显减少、账户绑定变了、发布状态为 unknown、凭据提交未决、部署后反复重启。先保存时间、页面提示和公开关联 ID，再按第六节排查。不要清空缓存来“证明”未缓存播放，也不要通过多次扫码掩盖未决事务。

2. 普通使用者的 10—15 分钟验收

准备一台电脑和你实际听歌的手机，记录浏览器、系统、网络和验收时间。先截图自己在同一个站点的歌单、收藏数和当前队列；验收期间若主动修改收藏或播放历史，要把这部分正常变化记下来。

步骤 操作 通过标准 不通过时记录
1 正常登录新站，打开“我喜欢”和曲库列表 能进入页面，原有列表与收藏可见，无反复登录 时间、入口、HTTP/页面提示
2 播放原先报错的收藏曲，再选两首不同歌曲 能听见声音，进度持续推进至少 30 秒；不能只看按钮变成暂停 曲名或公开曲目 ID、错误文案、是否所有曲目都失败
3 暂停后继续，把进度拖到歌曲中段 暂停与继续对应真实声音，拖动后从新位置播放，不无限缓冲 目标位置、实际位置、等待时长
4 手动下一首，再把一首歌拖近结尾并等待自然结束 手动切歌与自然跨曲都成功，队列顺序正确 队列、上一首与下一首、是否出现假结束
5 手机播放后切到其他应用，再锁屏等待自然跨曲 当前曲继续，锁屏后下一首能自动播放；记录实际等待时长 系统/浏览器、锁屏时刻、停在哪一步
6 使用锁屏或耳机控制播放/暂停；若系统支持，再测下一首 支持的动作确实改变播放；不支持时标“未支持/未验证” 控件是否出现、点击后实际声音
7 回到页面、刷新，再重新打开 页面曲目和真实播放状态可核对；收藏、歌单、排序仍在 页面状态与真实声音是否不一致
8 打开旧站做一次播放与列表核对 旧站仍可访问，其自身历史和列表未丢失 与该站发布前的差异

手机中断测试单独记。 有条件时测试来电/系统音频抢占、网络短暂断开再恢复、第二台设备独立播放。页面隐藏或锁屏不应被误当成来电而直接暂停；系统明确打断后默认暂停，不应突然自行出声。尚未做的项目标 not_tested，不要因为桌面播放通过就把 iOS、Android、耳机和跨设备全部签成通过。

以上是验收动作和通过标准，不是对每台设备已通过的声明。拖到结尾可以快速验证跨曲，但不能替代较长时间的后台播放测试。

3. 管理页面应该怎么看

管理员使用已有管理入口，不在浏览器里粘贴服务器 Bearer token。重点看账号、目录、音频、持久化等维度，以及观察时间、凭据版本和待处理动作。一个总的 healthy 或 degraded 标签不足以判断能否播放。

本次发布后，账号、目录、音频和持久化证据正常，但 player 仍为 not_tested；恢复账本与网关还存在历史版本差异。验收记录必须同时保留这两个事实，不能手工改账本让页面“变绿”。如果概要建议与各维度、时间戳不一致，应记录为状态展示问题，以实际接口和播放证据继续定位。

4. 可直接复制的验收记录

二、为什么做三个统一，以及现在统一了什么

音乐舱不是一个单独的播放器容器。浏览器使用 Any Listen；音乐扩展向 TS 网关请求目录和音频；恢复服务负责受控续期与登录协调；OpenClaw 插件连接 QQ；入口服务提供访问与管理边界。逐个手工更新时，很容易出现“代码已上传但进程没切换”“扩展还是旧版”“镜像标签相同但实际内容不同”。

最终选择是把发布交付集中在 music-cabin 仓库，继续固定 Any Listen 上游并应用仓库内补丁。没有把播放器全部复制进来长期分叉，也没有引入新的发布平台。旧 Go 网关和独立 kuake CLI 已退役；新发布不能再依赖它们作为运行组件或可播放的回退路径。

统一项 实现入口 解决的问题
版本 release/manifest.json、生成的 release.json、部署回执 输入、产物和运行状态各有依据，避免手填一个版本代表所有组件
构建 scripts/build-release.sh 固定上游和补丁，生成目标平台产物，校验后才形成完整发布包
部署 scripts/deploy-release.sh 先计划，再切换变化组件；重复执行可核对，异常不盲重放，回退保留数据

发布包包含六类组件：gateway、recovery、player、extension、plugin、entry。目标文件只声明本次管理的实例；未声明的旧站播放器与共享入口不会被顺带替换。

三、版本不是一个数字：三份清单怎样对应

1. 输入清单：固定“用什么构建”

Git 中的 release/manifest.json 固定上游完整 commit、补丁顺序与哈希、工具链、基础镜像 digest、目标平台和六组件定义。输入文件不写自己的 Git 提交号，避免自引用；构建时从干净工作区取得完整 HEAD。

七个补丁的顺序是 Media Session、诊断、后台预取、手机播放契约、元数据刷新、播放错误、维护者更新提示。缺补丁、顺序错误、前像不符或哈希不同，构建应失败，而不是尽量打上去继续发布。

2. 发布清单：记录“实际构建出了什么”

发布包根目录的 release.json 是生成物。releaseId 与 sourceCommit 等于构建时源码完整 SHA；它还记录输入清单哈希、平台、实际工具版本、组件和构件。每个构件记录相对路径、字节数及 SHA-256；每个组件记录构件集合及内容摘要。

verifyBundle 会拒绝缺失文件、未申报文件、路径越界、外层文件符号链接、哈希不符及不安全归档。归档解包还有嵌套与链接链检查。这是操作者选定发布包的完整性校验，不能夸大为第三方签名认证。

镜像至少区分本地构建 config digest、运行时镜像身份与 registry digest。本次生产 Docker 的 containerd image store 暴露 OCI manifest digest，和构建侧 config digest不一定相同。工具从已校验的镜像归档推导对应关系，不能只比较镜像标签，也不能把“未推镜像仓库”写成“已获得 registry digest”。

3. 部署回执：记录“真正运行了什么”

deployment.json 记录 deploymentId、releaseId、发布清单哈希、时间、状态，以及逐组件的 before/after 和检查结果。没有更新的组件保留原版本；未知来源明确为 null，不能补一个看似整齐的提交号。

四、执行前准备与发布步骤

1. 执行前准备

在有权限的发布工作机上准备 Node.js 24、npm 11、锁定的 pnpm、可用的 Docker/BuildKit、Git 和到目标机的 SSH。目标产物是 linux/amd64；Apple Silicon 可以通过模拟构建，但播放器原生模块仍须在 Linux 目标环境生成并验证，不能把 macOS 的二进制复制到服务器。

目标 JSON 使用已有私有配置，精确指定实例、端口、用户、工作目录、挂载、env-file 路径与检查项。仓库的 deploy/release/targets/example.json 只是结构示例，不是可以覆盖现有生产的配置。不得把 target 或 env-file 放进博客附件；读者需要向实例维护者取得属于自己的配置。

2. 独立检查发布包

预期 ok: true、errors: []，releaseId 与本次选定源码一致；以后比对部署回执中的 releaseManifestSha256。校验失败要重新取得或构建包，不能手改清单“修复哈希”。

3. 先 plan，再 apply

plan 不加载镜像、不停止服务、不改运行状态。检查 ready、preconditionBlockers、每个组件的 action/reasons，以及未受管理的实例。新发布允许出现预期的 replace；对已经发布的同一包验收时，应当是 noop: true 且全部 none。退出码 0 不等于 ready: true，必须读 JSON。

只有变更集和前置条件符合预期时执行：

apply 获取目标锁、复验发布包与配置，按依赖顺序更新变化组件，并写回执。容器可能经历 stop、rename、create、start，有短暂中断；这不是零停机发布。相同包与配置重复 apply 应为 no-op，但日常验收优先用 plan/status，不靠再次 apply 来验证幂等。

4. Caddy 配置如何真正生效

entry 使用受控 caddy-container 类型：先对候选执行 validate/adapt，再原地写宿主配置、重启既有入口并验证宿主文件、容器文件和运行配置。没有变化时不重启；入口镜像和外层共享 Caddy 不随配置发布重建。

这里不能只用 rename 替换文件。Docker 单文件 bind mount 可能仍钉住旧 inode，导致宿主看起来是新文件、容器仍读旧文件。工具以实际哈希和运行配置收口。生产采用 admin off 时，可以读取 autosave 核实；无法读到可靠运行配置就不能签署生效。重启既有容器不会重读 --env-file，密钥环境轮换需要单独重建，不能当作普通 Caddyfile 更新。

4. 音频验证不能被缓存蒙混过去

HTTP 206 和真实音频字节说明该样本的数据链路能返回音频；实际听到声音、进度推进还要靠播放器验收。ID3 是 MP3 样本的一种标记，不是 FLAC/M4A 等全部格式的统一通过标准。

缓存命中只能证明缓存读取和 Range 链路，不能证明当前夸克授权有效。未缓存验证需要可核实的缓存未命中证据，再结合该请求的上游访问与音频结果。当前统一工具可按缓存响应头分类；没有可信缓存头时，即使请求返回 206，也会把严格的未缓存证据标为 not_tested。不要改名当“新歌”、清掉生产缓存，或只凭第一次点击就签署上游验证通过。

本次生产回执中的两个普通 Range 检查通过，但 uncached-audio-evidence 为 not_tested，原因是网关没有可识别的缓存头。库存中没有同尺寸对象只是补充证据，不等同于完整的缓存未命中证明。若把该项设为必需，未验证就不能作为通过项发布。

5. 用户数据与版本验收

将同一站点发布前后的列表、收藏、排序与队列做比对。服务器证据应基于一致读取得到的表行数和内容摘要；只比较数据库文件大小或 WAL 文件哈希不足以判断数据是否丢失。真实播放会更新历史，播放器启动可能更新备份时间戳，需要逐字段解释正常差异，不能一句“所有文件完全一致”带过。

凭据、恢复账本、待提交事务与数据卷不属于代码回退内容。新的合法凭据提交若发生在验收期间，应记录其回执和版本推进；不能为了让前后哈希一样恢复旧文件。浏览器可见版本标识也只是辅助信息，运行镜像及构件哈希才是部署身份依据。

2. 媒体授权故障的经验

之前的 source not found 并非真的丢了音源：账号接口和取下载地址接口可用，但媒体直链拒绝请求；播放器的回退又覆盖了原始错误。已有受控刷新恢复了媒体授权，新协调器也补上了“账号健康但音频认证失败”触发刷新、失败后冷却且不自动升级为二维码的处理。

因此，“QQ 扫过码”“账号接口 200”和“未缓存歌曲可播放”是不同证据。再次故障时，应查登录操作回执、网关实际生效版本和同一曲目的媒体请求，不能只根据聊天中的成功提示要求用户无限重登。

七、这次已经验到了哪里
