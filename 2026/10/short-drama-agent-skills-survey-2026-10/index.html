短剧与漫剧 Agent Skills 调研：16 个仓库的机制、验证与可用边界

过去一个月，AI 短剧/漫剧方向的 Skill 仓库突然多了起来，标题都很像——“一句话到成片”“工业级流水线”“人设不崩、伏笔不丢”。但把仓库拉下来读一遍会发现，同样是 3K star，有的只是几百行提示词，有的真的带检查器、测试和出片链路；同样宣称"实测"，有的有提交回执，有的只有一份预期输出。

我把 16 个仓库全部克隆到本地，逐个读 SKILL.md、脚本和测试，并跑了它们零依赖的确定性自测（没有调用任何生成 API）。这篇文章回答三个问题——每个仓库到底有什么，哪些可以直接用，哪些只能看思路。

判断标准不看 star，看四样东西——工程机制（有没有检查器、状态文件、门禁脚本，还是纯提示词）、方法论沉淀（规则是否有判据、反例和失败模式，而不只是口号）、流程能走多远（停在文本，还是能到分镜图、视频提交、成片）、验证证据（自测、夹具、真实产出、成本记录）。16 个仓库之外，我自己的 ai-comic-skills 也作为对照放进了总表。

实测验证那一列还要打个折扣。"自测通过"只能证明工具逻辑正确，证明不了创作质量——这批仓库里真正跑到成片验证的只有两家，drama-skills 的 68 秒样片（外部视频，约 40 元）和 Micro-Drama 的任务提交回执，其余大多停在检查器自测层级。

1.1 第一梯队（机制、验证、流程完整度至少占两样）

drama-skills（MIT，3.4K star）是工程完整度最高的一个。每集只维护五份 Markdown——剧本、视觉设定、分镜、图片提示词、视频提示词——刻意不建数据库，理由是"改文件就是改决策层"。真正把它和其他仓库拉开距离的是连续性锁（Continuity Lock）。它把跨镜头必须保持的可见事实写成带 ID 的短语，例如 LOCK-JIANGCHEN-DRESS，锁面是 pine-green lapel service jacket；锁面必须逐字出现在图片提示词、冻结关键帧提示词、视频提示词三份正文里，粘在字母数字上的匹配不算，负面提示词里的匹配也不算；锁面只写"颜色 + 材质/形制 + 物体"，不写动作、状态、剧情。这几条边界看起来吹毛求疵，其实都是被真实漂移坑出来的。仓库带 29 个测试文件、713 个测试和 3338 个子测试，creator_markdown_check.py 能在公开样例上故意改坏两处后准确报错——这批仓库里唯一让我觉得"检查器真的会咬人"的实现。局限也要说清楚，它自己不生成视频，生产阶段要接外部 adapter；68 秒样片是 README 里的外部视频，不是仓库内可复现产物。

shuohao-skills（Apache-2.0，5.3K star）的验证强度第一。7 个 skill 边界切得很干净——大纲、人物、美术、剧本、站位、分镜，加一个真正出图的 character-refs。最值得学的是确定性 seed，每个节拍几秒由脚本算出来，模型只负责切镜，"模型瞎估时长"这种常见漂移被直接消灭。分镜有 18 道质量门，全部代码化；.gates.jsonl 还会统计哪道门最常响、哪道门从没响过，把规则库当产品在运营。我实际跑了 7 个 skill 的自测和报告自测，1559 + 92 项断言全绿，这在开源 Skill 里非常少见。局限在于只有 character-refs 真出图，全链路不出视频；README 声明只在 macOS + Node 24 验过。

ai-comic-drama-director-skills（MIT，15 star）把规则做成了可执行的三件套，每个 skill 都是"规则 + validator + 单测"，37 个 Python 脚本，149 个测试全过，工程化程度高于 star 更多的 ManjuForge 和 OnlyShot。ai-shot-execution-continuity 的 12 步检查非常实战，覆盖第一帧、空间阻挡、摄影机轴线、道具手、光线物理、语言触发、切镜继承、跨组继承、局部修复锁；测试里甚至有"8 秒连续表演不默认切镜""跨组同角色特写硬切应拒绝"这类语义断言，不止测字段存在。局限在于仍是 prompt-only，没有记忆文件、没有出片链路，文档偏作者个人工作流，通用性需要改写。

1.2 第二梯队（有真机制，但有明显短板）

ManjuForge（MIT-0，24 star）的记忆机制最深——七个记忆文件加三套引擎（Story Bible、Character Graph、Foreshadow Engine），22 项跨文件检查加 18 项单集检查，结构是这批里最完整的。报错格式值得直接抄，每条同时给出哪两个文件在哪一点矛盾、怎么修。但 demo 跑它自己的检查器，结果是 8 红 / 7 黄 / 3 绿——缺 场景布局.md、E6 剧情摘要缺林老太君、6 处碎片时间轴空档。README 写明了"检查器在 Demo 上抓出这些问题"，谈不上造假，问题在于把检查器演示和干净基线混在了一起；"伏笔回收率 100%“的表述同样有歧义，伏笔表 12 根里只有 2 根已回收，其余 10 根活跃，100% 指的是全部有回收或推进。结论是抄它的检查器和记忆分层，不要把它当"已验证的干净模板”。

manju-laoli-skill（MIT，1.7K star）规则最厚，也重到需要专用基础设施——13 个 skill、19 个脚本、六道前置锁加画风锁、契约核销、上下文切片、约 130 个机检码，9 项稳定性测试通过。它最聪明的一点是 M0/M1/M2 素材形态，承认"图不在我手里"，把图片入库从阻塞条件降级为可选登记，这是对"prompt-only 工具如何不卡死"的正确回答。代价是 2.8MB 规则、单文件 5.7 万汉字当量，没有它的 slice_context.py 根本跑不动，中小项目抄这套会先被上下文压死。

OnlyShot（MIT，339 star）产线经验最真，证据也最薄。17 个失败模式全是真金白银——3 类 fail 区分（字数超 / 审核 / 网络）、1500 字符硬上限、反派词替换表、长 prompt 必单跑、静态图成本是视频的 1/18；三阶段成本分层（剧本 → 分镜图锁构图 → 视频）是短剧生产最该学的经济账。但仓库里只有 1 份 eval 用例（21 条断言），没有跑分结果，也没有任何生成产物，默认工作区还写死了 Windows 路径 D:\hrdai\。

Micro-Drama-Skills（无 License，326 star）是唯一真跑到提交的——4 个 skill、5 个样例项目、352 张 PNG，DM-003 有 10 条真实 taskCodes；seedance_project_tasks.json 的 (@ref.png) 引用、base64 展开、submission_report.json 是一套完整可抄的交付协议。硬伤同样明确——无 License，写死 /data/dongman/ 和 localhost:3456，强绑 Gemini 加 Seedance。技术上有价值，法律上不能复制。

1.3 第三梯队（单点优秀或偏薄）

偏薄的项目里有四个连 License 都没有。spark-video 是真端到端代码，render、TTS、stitch、review 和 4 道 gate 都有，但绑阿里云百炼，仓库无产出。jingju-skills 有 6 种状态标签、10 阶段门禁和 3 个 JSON 模板，全是散文没有脚本。ai-manga-drama 三个 md 写死个人路径，调 neta CLI。awesome-ai-micro-drama 只有一份 README，忽略。

有 License 但单点突出的也有四个。short-drama-factory（MIT）的 E1~E26 单集机检加 S1~S8 台账机检是剧本层最扎实的，不管分镜、资产和视频。screenwriter-skill（MIT）是 38 条创作铁律的单点规则库。seedance2-skill（MIT，4.4K star）是纯提示词生成器，无脚本。awesome-short-drama-skills（CC0）是带 eval harness 的索引层，适合用来找项目，本身不是 skill。

二、能用什么，该学什么

先说可以直接用或二次开发的八个项目，License 都允许，按对我的价值排序。

项目 License 怎么用
drama-skills MIT 首选工程参考，连续性锁、五文档模型、检查器、713 测试可直接学，代码可复用
shuohao-skills Apache-2.0 首选验证体系，18 道门、1651 项断言、确定性 seed 适合做质量底座
ai-comic-drama-director-skills MIT 首选"规则可执行化"参考，149 个测试是现成模板
short-drama-factory MIT 只做剧本层可直接用，E1~E26 机检可单独拿
OnlyShot MIT 产线经验和失败模式可直接用，路径要改
ManjuForge MIT-0 记忆机制可参考，检查器可用，demo 不能当干净基线
manju-laoli MIT 能接受重型流程和切片器时才用
screenwriter / seedance2 MIT 单点参考，不值得整套引入

没有 License 的五个仓库——Micro-Drama-Skills、spark-video、ai-manga-drama、jingju-skills、awesome-ai-micro-drama——只能读思路。没有 License 不等于没有价值，但默认版权是"保留所有权利"，任务 JSON 设计、门禁顺序、失败模式都可以读，代码、提示词原文和文档不要复制；确实要用的，先联系作者拿授权。

另有三个项目不建议整包引入。manju-laoli 规则墙太重，没有配套切片器会稀释注意力；spark-video 是 Python/uv/ffmpeg 重栈加单一供应商，除非确定要自己跑完整渲染；Micro-Drama 则是 License、绝对路径、本地服务三重耦合。

如果只记 7 件事，我选下表这些。

机制 出处 学什么
连续性锁 drama-skills 把"跨镜不变的事实"写成可逐字校验的锁面，三份正文都要出现
跨文件报错格式 ManjuForge 每条问题说清哪两个文件在哪一点矛盾、怎么修
确定性 seed + 质量门 shuohao 秒数由脚本算，模型只切镜；每道门有击穿用例
规则 + validator + 单测三件套 ai-comic-drama-director 每条规则都能被代码验证
成本分层 OnlyShot 先静态图锁构图再烧视频钱，明确成本比
项目状态/决策记录 drama-skills、shuohao、jingju 跨会话恢复不靠扫描目录
契约核销 + 上下文切片 manju-laoli 流程大到需要它时才用

对应的坑有五个。规则墙，2.8MB 的规则库没有切片器就是灾难；绝对路径，D:\hrdai\、/data/dongman/、/Users/yves/ 都是作者本机工作区，产品设计里不该出现；无 License 的代码，技术上能跑，法律上不能复制；手动记忆同步，七个记忆文件靠模型自觉更新，迁移到长项目必然漂移；为出片自建重栈，先用 adapter 契约接一个可用后端，不要一上来重写渲染管线。

这份清单最后落回我自己的 ai-comic-skills。它现在有 4 个 skill——script、visual-assets、storyboard、video-prompts，链路是完整的，文案和防覆盖规则也写得不错。对照上面的标准，差距很清楚。

维度 现状 差距
工程机制 0 脚本、0 检查器、0 状态文件 所有质检都是散文表格里的勾选符号
方法论 4 份 SKILL + 3 份 checklist 有检查项，没有判据、反例、退出码
流程 到提示词表为止 不生成图、不生成视频、不剪片
证据 3 个 eval 用例 没有跑分结果、没有 demo

落地顺序分三步。P0 补机制——在 visual-assets 里加 LOCK-* 连续性锁；分镜表加"视觉依据"列；写 check_continuity.py（逐字校验、负面词排除、粘词排除）和 validate_storyboard.py（镜号、时长、台词逐字、素材存在、总时长）；再配干净 fixture 和故意改坏的 fixture，证明检查器会咬人。

P1 补证据——加 project-state.json，把跨会话续作从"扫目录"升级成"读状态"；跑一部 3 集 demo，公开输入、输出、失败修复记录和成本；把 3 个 eval 用例真正跑一遍并记录结果。

P2 接后端——加 produce skill，走 preview → explicit confirm → run；接一个实际能用的视频后端，保留 prompt-only fallback。

三、学习优先级：先吃透这 5 个

前面两节回答的是"能用什么"，这一节回答"先学什么"。16 个仓库不可能都吃透，挑选是一个四步过滤。第一步按 License 过滤，无 License 的 5 个仓库只能读思路、不能抄代码，直接出局；第二步按"机制独有"过滤，教的东西别的仓库也覆盖的单点工具出局（纯规则库、提示词生成器、索引站）；第三步按"验证强度"排序，优先留有可跑自测和负向断言的仓库——"我宣称有规则"和"我的规则被测试盯着"是两回事；第四步按"缺口对口"收口，ai-comic-skills 缺的是工程机制、验证、记忆和成本视角，不是剧本文案，剧本层专用工具在这一步让位。

16 个仓库减去 5 个入选，再减去 ai-comic-skills 自己（对照物，不参选），剩 10 个落选。每一步淘汰了谁、为什么，见下面两张表。

入选的 5 个如下，按学习优先级排序。
